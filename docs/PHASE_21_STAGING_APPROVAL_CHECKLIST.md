## 1. Architecture decision for review

**Preferred conditional staging candidate:** one DigitalOcean Basic **8 GiB / 4 vCPU** Droplet in **BLR1 (Bangalore)** runs Nginx, the static Vite build, two FastAPI workers, and a co-located `clamd` reached by a private Unix socket. Nginx serves the frontend and proxies `/api` on the **same approved HTTPS origin** to the API bound to loopback. A dedicated encrypted **50 GiB DigitalOcean Volume** holds four private laboratory/clinical approved and quarantine directories under `STAGING_STORAGE_ROOT`. A separate **DigitalOcean Managed MongoDB 2 GiB, single-node** staging cluster in the same BLR1 VPC is the database candidate. It must have the exact `physiocare_staging` database identity, private hostname, restricted trusted sources, a database-scoped `readWrite` application user, and validated TLS. Daily Droplet backup, encrypted file backup, managed Mongo backup, monitoring and a separate restore destination complete the candidate. Payments and reconciliation remain disabled.

**Why this revises Phase 20:** `frontend/src/services/api.js` defaults to `/api` and sends credentials; `backend/app/api/auth.py` sets host-bound `SameSite=Lax` cookies. A frontend on an unrelated `pages.dev` site with an API on another registrable domain would not reliably exercise the real browser session. One origin also removes cross-site cookie complexity while keeping exact CORS and CSRF checks. [BLR1 supports Droplets](https://docs.digitalocean.com/platform/regional-availability/), [Managed MongoDB](https://docs.digitalocean.com/products/databases/mongodb/details/availability/), [Volumes](https://docs.digitalocean.com/products/volumes/details/availability/) and [Spaces Standard](https://docs.digitalocean.com/products/spaces/details/availability/). Same-provider private VPC connectivity is [documented](https://docs.digitalocean.com/products/databases/mongodb/concepts/best-practices/). This is a location candidate, **not** a clinic-approved data-residency choice.

**Sizing and database are conditional.** [ClamAV guidance](https://docs.clamav.net/manual/Installing/Docker.html) suggests 3–4 GiB RAM; an 8 GiB host may be tight with two API workers and signature updates. Before PDF/browser acceptance, measure peak RSS, OOM/restarts, scan latency and two-worker load. Upgrade the same host to **16 GiB / 8 vCPU** if it misses agreed headroom or scan-time limits. DigitalOcean calls its single-node Mongo plan preliminary testing rather than highly available; whether the selected single-node service exposes the replica-set and transaction behavior required by PhysioCare is **UNVERIFIED**. Provider API documentation references [multi-document transaction lifetime](https://docs.digitalocean.com/reference/api/reference/databases/), but that is not proof for the chosen plan. Before application writes, independently verify `hello.setName`, writable PRIMARY, sessions, feature compatibility, TLS and a synthetic rollback; if any fail, do not run connected workflows. Re-quote a three-node DO managed replica set or Atlas M10+ in an approved network topology. The present local Phase 15 transaction success does not prove a cloud provider tier.

**Suitability assessment:** same-origin HTTPS can support current web and authenticated browser tests after ingress/CSRF validation; private VPC Mongo can support two-worker throttling and report/account transactions only after identity/transaction proof; the host plus POSIX Volume can support scanning and atomic promotion only after daemon/filesystem proof; backup/restore is possible but must be demonstrated. Native mobile integration can reuse a versioned HTTPS API later, but current browser cookie/CSRF behavior does **not** establish a reviewed native-client credential flow. Mobile app design, secure cookie storage, certificate handling, rate limits, API compatibility and push notifications need a later separate review. No mobile infrastructure purchase is justified now.

## 4. Network, application and data controls

**Proposed path:** browser → one approved HTTPS staging origin → Nginx static routes and `/api` proxy → two API workers on loopback → private BLR1 VPC → scoped managed Mongo. Keep `VITE_API_URL` unset for same-origin `/api`; if a future mobile or split-origin client is approved, use an explicit reviewed URL and origin policy. Set exact HTTPS `CORS_ORIGINS` even with same-origin traffic; reject wildcard. Nginx must overwrite, not append untrusted, `X-Forwarded-For`; `TRUSTED_PROXY_NETWORKS` must contain only the actual direct proxy CIDR. Review Uvicorn proxy-header handling so it does not independently trust a wider source. Direct API, Mongo, scanner socket and admin ports must not be internet-reachable. Provider docs say managed Mongo is [publicly accessible by default until trusted sources are set](https://docs.digitalocean.com/products/databases/mongodb/how-to/manage-users-and-databases/): configure narrow private trusted sources and reject `0.0.0.0/0` before any application connection.

`backend/staging.env.example` is a **template**, not a deployable configuration: its empty JWT values, `TRUSTED_PROXY_NETWORKS=[]`, placeholder host/origin and disabled scanner must be replaced through approved secret/config injection. The runtime guard requires exact `STAGING_INSTANCE_ID=physiocare-isolated-staging`, `DATABASE_NAME=STAGING_DATABASE_NAME=physiocare_staging`, a non-local URI host matching `STAGING_DATABASE_HOST`, credentials, `tls=true`/`ssl=true`, verified certificate and hostname, HTTPS CORS, private contained storage paths and enabled Mongo-backed auth throttling. Initial staging must keep demo modes, payments and reconciliation disabled. The API process must start with explicit `ENVIRONMENT=staging`, no development reload, ASGI lifespan on, and a reviewed non-root process manager. The `/health` route is lightweight; it is **not** dependency readiness. Source evidence: `backend/app/core/config.py`, `backend/app/main.py`, `backend/staging.env.example`.

**Storage/scanner:** the four report/quarantine roots must be private, non-overlapping and on the same mounted filesystem for atomic `os.replace` promotion. The Volume is [encrypted at rest](https://docs.digitalocean.com/products/volumes/details/features/); verify 0700/0600 permissions, mount ownership, persistence, free space, no public static alias and encrypted backup export. `clamd` must share the API host's private Unix socket, have approved signature updates, startup PING, freshness alert and safe malware-fixture/outage tests. With scanner disabled, PDF uploads fail closed; scanner-disabled startup is not a completed PDF gate. Cleanup reconciler is an explicit controlled operation, with DB-health precheck and pending-cleanup alerts. On a single host, worker failure can be tested; host failure requires restore and is a staging limitation.

**Future mobile:** do not add bearer-token shortcuts or weaken CSRF to support a native app. A later mobile integration must define secure session/cookie storage or a separately reviewed token contract, profile fetch, logout/revocation, certificate validation, device loss, API version compatibility, and rate-limit identity. The staging HTTPS API can be reused after this review. No mobile client exists in the assessed web scope.

## 6. Fictional-data policy proposed for approval

Only run-scoped synthetic patients, therapists, administrators, receptionists and laboratorians; invented names, reserved example-domain addresses, non-routable contacts, fabricated appointment/care-plan/lab findings, and clearly marked synthetic PDFs. Do not import production dumps, real names/phones/records, clinical PDFs, live provider keys or actual payment events. Synthetic payment scenarios stay offline initially; Razorpay Test Mode requires a separately approved payment-enabled design. Privacy/project owner **UNASSIGNED** must approve source provenance and a pre-run manifest; security operator **UNASSIGNED** enforces access, audit and redacted evidence. Restrict staging and backup access to named staff with MFA and least privilege.

**Retention proposal, not approved policy:** capture case evidence, then remove run-scoped records and private files within 24 hours under a preapproved cleanup manifest; run a nightly orphan review; retain sanitized app logs at most 30 days. DO managed Mongo backups retain seven days by provider default; private file-backup retention must be chosen to match the approved recovery requirement. Any request for 30-day backup retention needs a separately costed design. Verify synthetic provenance before ingest and independent counts/file inventory after cleanup. Indexes and collections may remain after a test, so record exact expected residual schema; never claim an empty database solely because records are gone. No deletion or backup operation is authorized now.
