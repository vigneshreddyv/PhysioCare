## Phase 23A — authentication and session review

The `/auth/login` route calls the rate limiter, then `AuthService.login`, and issues cookies only after that returns. The service verifies a password hash even for an unknown account, combines invalid password and inactive status into the same `401 Incorrect email or password`, creates hashed refresh/CSRF session state, and returns the bundle only after persistence. The service's inactive and active login tests passed. The middleware validates access JWT type/signature/session binding, revocation and expiry, CSRF on unsafe methods, then current user activity. Refresh atomically claims and rotates the refresh hash, validates active user, and rejects replay; `/auth/csrf` uses the same active refresh-session check. Logout checks CSRF, validates refresh session when supplied, revokes server state and then clears cookies. Frontend sign-out hides private data while revocation remains unconfirmed and offers retry; login waits for `/auth/me` before protected navigation.

**Status: FIXED for the original inactive-session issuance path; connected behavior BLOCKED.** The reviewed tests use a doctor model for the specific inactive-login case and do not run a full patient/doctor/admin HTTP matrix or a connected deactivation race. Such gaps are test coverage limits, not evidence of a bypass. Cookie Secure/SameSite behavior depends on correctly selected staging/production configuration and real HTTPS ingress.

## Phase 23B — PDF delivery and sensitive responses

Uploads still pass through private quarantine, structural checks and fail-closed scanner verdicts; no real daemon or ingress was exercised.

## Phase 23C — clinical pagination and authorization

`page_window()` rejects zero, negative, noninteger, page above 1000 and page size above 100. Appointments, reports, lab requests, care plans, exercise assignments/progress, home visits, notifications, patient directories and patient histories pass a `PageWindow` from role-gated API routes to repository queries. The repositories filter ownership/assignment before `skip` and `limit`, sort by the domain date and `_id`, and retain the existing response arrays or nested history shape. Doctor history checks assignment independently of page emptiness, preserving the neutral missing/unassigned 404 contract. The patient lab route derives patient ownership from the authenticated profile rather than a supplied query parameter. Static tied-date tests cover no duplicate report IDs over pages, including empty last page. The direct route/repository tests are mocks, so connected query behavior and concurrent-write page consistency are **BLOCKED**.

**Status: FIXED for the identified unbounded API list paths under offline tests; overall finding IMPLEMENTED.** The doctor released-report route still builds a distinct list of every assigned patient ID before its paged lab query. The old unpaged methods remain callable internally. Patient/reception directory filtering can create sparse database pages, which the frontend scans until an empty page. Schedule conflicts are not paged: they must inspect every candidate in the relevant time window to avoid false availability.
